# Is Post-Training the Answer? Transforming GLM 5.2 with Bolt-On Expert LoRA

## I. Introduction

Do you follow derivative models?

To be honest, I didn't use to. Models built on top of other models — their capabilities are determined by the underlying model, giving them a feel of knockoffs versus originals — nothing worth paying attention to.

But I recently met a friend who changed my perspective.

He said many cutting-edge teams are actually exploring the "derivative model" path. In these labs, many believe that **post-training is currently the area with the most innovation**.

For model development, creating derivative models is actually more rational. **Someone else spent a fortune training weights and open-sourced them for free — why not take advantage?** Making some enhancements to the original model to get desired results at lower cost — that's worth exploring.

That sounds quite reasonable.

He further explained that they're currently building a reinforcement learning model called [Macaron V1](https://macaron.im/mindlab/research/introducing-macaron-v1), based on the popular GLM 5.2, with post-training and feature enhancements.

![](https://cdn.beekka.com/blogimg/asset/202607/bg2026072214.webp)

GLM 5.2 already scores well. After their modifications, internal benchmarks showed even higher scores.

![](https://cdn.beekka.com/blogimg/asset/202607/bg2026072213.webp)

In the image above, blue bars are Macaron V1, green bars are GLM 5.2.

Let me explain their approach — how to develop based on someone else's model. This will help you understand how derivative models come about.

## II

Their method is called Mixture-of-LoRA (MoL).

From my understanding, the MoL architecture looks something like this diagram below. I drew it — may not be entirely accurate.

![](https://cdn.beekka.com/blogimg/asset/202607/bg2026072003.webp)

Simply put, it adds an extra routing layer with four 1B-parameter LoRA experts (sub-models) attached underneath.

LoRA stands for Low Rank, indicating these experts are lower-level than GLM 5.2's built-in experts.

When the routing layer receives user input, it selects one of the four experts to process the input. The expert's result is then weighted and fused with the original GLM 5.2 model's result to produce the final output.

The advantage of this structure is that **experts are bolt-on — they can be added as needed without disturbing existing knowledge**. Different experts can also be combined. Need a domain expert? Just bolt one on — no need to modify the original model.

Some readers may have noticed that this MoL architecture resembles Mixture of Experts (MoE). Indeed, I think the principle is the same. The difference is that **MoE uses internal experts within the model, while MoL uses external experts attached to the model**.

## III

Going back to the diagram above, Macaron V1 has four external experts attached:

> - LoRA0: Chat
> - LoRA1: Agent (corresponding to OpenClaw capabilities)
> - LoRA2: Coding
> - LoRA3: Visual Rendering (UI4A)

These are the four capabilities it optimized for GLM 5.2, aiming to fine-tune the original model's behavior to better meet user needs.

These bolt-on experts not only enhance capabilities but can also change many parameters of the original model.

For example, GLM 5.2's context window is 1M tokens, but Macaron V1 increases it to 2M. They've open-sourced this method under the project name [LongStraw](https://github.com/MindLab-Research/longstraw), which seems applicable to various models for expanding existing context windows.

At this point, it should be clear that **derivative models aren't simple copies of the original — they're deeply processed, capable of changing behavior and enhancing features**.

## V

Next, testing code capability. The request was to generate a 2D web game "Angry Birds."

Macaron V1 and GLM 5.2 had similar UIs — the bird and brick styles were very close, confirming Macaron V1 is indeed derived from GLM 5.2.

However, Macaron V1 clearly implemented better — not only adding pigs on top of the bricks but also making the brick collision effects more vivid, with stronger gameplay. This suggests the external Coding expert is working.

I also tested the recently released Kimi K3 by asking it to generate Angry Birds. For some reason, the result was quite poor — the bird couldn't even be launched.

## VI

Macaron V1 also has a unique feature that GLM 5.2 lacks: **the visual rendering expert UI4A**. It can visually display model-generated results in real-time in a web window.

This feature works best with the open-source tool [macaron-artifacts](https://github.com/mindverse-ltd/macaron-artifacts) — a customized large model web interface that implements UI4A's visual display.

After installation, it starts a local service at `http://localhost:7878`, serving as a browser-based large model web frontend.

![](https://cdn.beekka.com/blogimg/asset/202607/bg2026072005.webp)

This dialog box displays results visually — conversation results are shown graphically, and users can interact with the graphics.

For example, if you ask to generate a 3D Rubik's Cube, it displays it in real-time, and you can directly manipulate the cube in the window.

For comparison, GLM 5.2's [official web interface](https://bigmodel.cn/trialcenter/modeltrial?text&modelCode=glm-5.2) would only show code and text for the same prompt (shown below).

![](https://cdn.beekka.com/blogimg/asset/202607/bg2026072101.webp)

## VII

From the simple tests above, Macaron's coding performance is somewhat better than GLM 5.2, and it adds its own features such as more natural dialogue, GUI, and 2M long context.

As a derivative of GLM 5.2, **Macaron V1 not only has GLM 5.2's functionality and performance but also deepens and extends it**, optimizing code generation results.

In terms of pricing, both are the same.

![](https://cdn.beekka.com/blogimg/asset/202607/bg2026072215.webp)

Therefore, for personal daily use, this model is worth considering. It's essentially GLM 5.2 + four external experts, all tailored for personal life scenarios (chat, Agent, coding, and visual rendering) — very practical.

In short, **when you're considering using a particular large model, also pay attention to its derivative models — they might sometimes be the better choice**.
